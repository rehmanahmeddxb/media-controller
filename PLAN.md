# Part I — Specification

## 1. Product definition

Ahmed Reaction Studio is a **local-first browser video studio** for creating reaction, commentary, comparison, tutorial, and multi-source videos.

It must support:

- One main canvas.
- Multiple independent PiP/overlay media layers.
- Local video files and camera sources.
- Independent play/pause/seek per media layer.
- Per-layer show/hide.
- Add / remove / reorder PiP layers.
- Draggable, resizable PiP rectangles.
- Four corner handles + four side handles.
- Presets for common PiP layouts.
- 16:9, 9:16 and 1:1 canvases.
- Android: maximum 2 physical camera sources.
- Windows: multiple cameras, limited only by hardware/browser/device capability.
- A local high-performance preview pipeline.
- Independent timeline events.
- Local recording.
- Final high-quality FFmpeg rendering.
- Adaptive proxies for heavy media.
- Multiple export formats and resolutions.
- No cloud dependency.
- **Original files are never modified or deleted by the application.**

## 2. Technology decisions

**Frontend — browser-native, buildless, and lightweight:** HTML5, CSS3, **Vanilla Modern JavaScript (ES Modules)**, Canvas 2D, `HTMLVideoElement`, `MediaDevices`/`getUserMedia`, `MediaRecorder`, Web Audio API, Pointer Events, `requestVideoFrameCallback()` (with `requestAnimationFrame()` fallback), File System Access API where supported, Web Workers where useful, OffscreenCanvas where supported and beneficial.

**Explicitly not used in v1:** React, Electron, Node.js backend, npm, TypeScript build toolchains, heavy UI frameworks, Django. All frontend code is clean, native modern JavaScript (ES Modules) served directly as static files by FastAPI without any bundling, transpilation, or npm build steps. The browser natively executes ES Modules and provides all required media primitives directly.

**Backend:** Python 3.11+, FastAPI, Uvicorn, Pydantic, python-multipart, aiofiles. Python is the orchestration/control layer — it must **never** process every video frame itself.

**Media engine:** FFmpeg + FFprobe (authoritative). FFmpeg handles decoding, normalization, proxy generation, scaling, padding, cropping, PiP compositing, audio processing, timestamp correction, frame-rate conversion, encoding, muxing, final export and validation. FFprobe handles codec detection, resolution, FPS, duration, audio streams, pixel format, HDR info, VFR/CFR detection, bitrate and stream validation.

**Optional future engine:** GStreamer. Not mandatory for v1; may be introduced later only if benchmarking proves a specific local real-time pipeline benefits. The architecture keeps it pluggable rather than making the project depend on it.

## 3. Local-first rule

There is **no** PythonAnywhere dependency in v1: no cloud processing, no mandatory cloud storage, no remote media upload, no remote FFmpeg, no remote database, no internet requirement for normal editing. Everything stays on the user's device. PythonAnywhere may be considered later for optional account/project sync, but it is explicitly outside v1.

## 4. Platform support

- **Windows:** Python, FastAPI/Uvicorn, FFmpeg, FFprobe, Chrome/Edge/Firefox. Started via `scripts/start_windows.bat`.
- **Android:** Termux, Python, FastAPI/Uvicorn, FFmpeg, Android browser. Started via `scripts/start_termux.sh`. Just `pkg install python ffmpeg`, install requirements via `pip`, and run. The browser handles camera permissions; Termux does not need direct camera-hardware control for the normal workflow.

## 5. Architecture

```text
             LOCAL DEVICE
                  |
       +----------+----------+
       |                     |
   BROWSER UI             FASTAPI
  (Vanilla JS)      Project / Jobs /
  [ES Modules]        Media control
       |                     |
       +----------+----------+
                  |
             Local Storage
                  |
               FFmpeg
                  |
             Final Export
```

The design intentionally separates: **real-time interaction → browser (Vanilla JavaScript ES Modules)**, **application orchestration → Python**, **heavy authoritative media processing → FFmpeg**. This is the strongest practical architecture for a lightweight local reaction studio with zero npm dependencies and zero cloud dependency.

## 6. Media source model

Every media layer is a source object with its own independent media element and state.

```json
{ "id": "layer_01", "type": "video", "source": "local", "name": "Main Video",
  "file": "...", "visible": true, "muted": false, "volume": 1.0, "playing": true }
```

```json
{ "id": "camera_01", "type": "camera", "deviceId": "...",
  "visible": true, "muted": false, "volume": 1.0 }
```

Never use one shared media element for multiple independently controlled layers. A source may be reusable in more than one layer, but each reuse gets its own media element instance.

## 7. Canvas

One master canvas per project. Aspect ratios: 16:9 (logical 1920×1080), 9:16 (1080×1920), 1:1 (1080×1080), scalable to other export resolutions. The displayed canvas is responsive; the **logical render coordinate system stays stable**.

## 8. Multi-layer PiP system

The single-PiP model is replaced by a **multi-layer compositor**:

```text
Layer 0: Main video
Layer 1: Camera 1
Layer 2: Camera 2
Layer 3: Local video A
...
```

The user can add, remove, duplicate, rename, reorder, hide, show, lock, mute, change volume, move, resize, and apply presets to PiP layers. Each PiP is assigned independently (`PiP 1 → Camera 1`, `PiP 2 → local_clip.webm`, …).

**Layer panel** (one row per layer) exposes visibility, lock, mute, volume, play/pause, rename, delete and drag-reorder. The selected layer gets editing handles on the canvas.

**Z-order:** higher layer = drawn later. Users drag layers up/down and the renderer uses the same order.

## 9. Cameras

- **Android v1: maximum 2 camera sources.** Detect available devices; show one if only one is available; allow both if two are. If the browser/device cannot expose two simultaneous streams, the UI must clearly report that limitation rather than pretending. **No fake multi-camera behaviour.**
- **Windows: capability-based multi-camera.** Enumerate devices via MediaDevices and assign any available camera to a layer. The real simultaneous count is limited by USB bandwidth, driver, browser, CPU/GPU, RAM and capture resolution/FPS. Detect failures and degrade gracefully.

## 10. Visibility semantics

Every layer has `Visible: ON/OFF`. When hidden it disappears from the canvas; its media state continues per project policy; visibility changes are recorded as timeline events.

**Hide/show is different from pause/play:**

```text
playing + hidden  -> keeps playing, invisible
paused  + visible -> visible on its current frame
paused  + hidden  -> paused and invisible
```

## 11. PiP geometry and editing

Geometry is normalized 0–1 so layouts are resolution-independent:

```json
{ "x": 0.70, "y": 0.70, "w": 0.25, "h": 0.25 }
```

- **Dragging** changes `x`/`y`; the layer stays within canvas bounds unless an explicit "allow outside canvas" mode is implemented. Pointer Events support mouse, touch and stylus, with pointer capture during drag.
- **Eight handles** per selected layer:

  ```text
  ●──────●──────●
  │             │
  ●             ●
  │             │
  ●──────●──────●
  ```

  Corner handles modify width and height (anchored at the opposite corner); side handles modify one dimension only (left/right → width, top/bottom → height). Optional aspect-lock. All geometry is clamped and validated.
- **Presets:** top-left, top-center, top-right, center-left, center, center-right, bottom-left, bottom-center, bottom-right, 50/50, 70/30, full-screen, quarter-screen, custom — all must work regardless of canvas aspect ratio.

## 12. Independent media controls

Every layer has independent play, pause, seek, volume, mute and visibility. **No global pause may unintentionally pause all layers.** Global Play All / Pause All / Reset All may be offered as a separate explicit control, but individual controls remain authoritative.

## 13. Timeline and synchronization

Every meaningful media action becomes an event:

```json
{ "layerId": "camera_01", "action": "pause", "wallMs": 12843, "mediaTime": 7.233 }
```

Event types: `play`, `pause`, `seek`, `visibility_on`, `visibility_off`, `mute`, `unmute`, `volume`, `source_change`, `geometry_change`, `layer_add`, `layer_remove`, `layer_reorder`.

The master recording clock uses `performance.now()`. **Never synchronize independent media by frame number.** This supports different FPS, VFR, independent pauses, independent seeks, camera timing and visibility changes.

```text
                MASTER CLOCK (performance.now())
                     |
      +--------------+--------------+
      |              |              |
    Main         Camera 1        Camera 2
   timeline      timeline        timeline
      |              |              |
      +--------------+--------------+
                     |
                 Event log -> FFmpeg renderer
```

## 14. Preview pipeline

```text
Media Source -> HTMLVideoElement -> requestVideoFrameCallback() -> Canvas compositor -> Display
```

Fallback to `requestAnimationFrame()` when rVFC is unavailable. **Do not use Python/OpenCV for live preview.**

## 15. Audio pipeline

```text
Media Element -> MediaElementSource -> GainNode -> Mute/Volume -> Audio Mixer -> MediaStreamDestination
```

The recording stream combines the canvas video track with the mixed audio track. The audio system must preserve synchronization with the master clock.

## 16. Recording

Recording starts with a configurable countdown (3 → 2 → 1 → RECORD) and captures the compositor video, mixed audio, event timeline and project state. Where practical, camera/source recordings are also preserved separately so final rendering does not depend solely on the browser-composited recording.

## 17. Local file handling and large files

Users select files through `<input type=file>` or the File System Access API where supported. The app must not assume it can browse arbitrary disk paths from a web page; Android uses the system picker. Large media is never sent to a remote server: use browser-selected local files, object URLs for preview, and retain source `File` references for the session.

## 18. Adaptive proxy system

Inspect media before previewing: resolution, codec, pixel format, FPS, bitrate, VFR, HDR, duration, audio.

```text
Original
   +-- device handles it --> Original preview
   +-- too heavy ----------> 1080p proxy
   +-- still heavy --------> 720p proxy
   +-- still heavy --------> 480p proxy
```

Do not create unnecessary proxies; originals are never replaced.

## 19. Playback health and stutter prevention

Track decoded frames, dropped frames, current FPS, target FPS, buffer state, render time, compositor time, audio drift, camera frame stability.

```text
TARGET FPS: 60
ACTUAL FPS: 59.7
DROPPED: 0
AUDIO DRIFT: 1.1 ms
STATUS: EXCELLENT
```

If performance degrades, in order: reduce preview resolution → reduce preview FPS if necessary → switch to a lighter proxy → reduce compositor workload → enter safe preview mode. **Never degrade final export quality.**

Never: decode every frame in Python, re-encode originals unnecessarily, upload local media, make expensive synchronous API calls during playback, block the main thread with heavy processing, continuously recreate media elements, or repeatedly create `MediaElementSource` nodes for the same element. Prefer hardware/browser decoding, rVFC, lightweight Canvas operations, cached media elements, Web Workers, adaptive proxies and local FFmpeg for heavy work.

## 20. Final rendering

Final rendering is authoritative. Inputs: original media, camera recordings, timeline, visibility events, PiP geometry, layer order, audio settings, output settings.

```text
Original Sources + Camera Recordings + Timeline + Layer Geometry + Audio Configuration
    -> Timeline Reconstruction -> Scale/Padding -> Multi-layer Overlay
    -> Audio Mix -> Timestamp Normalization -> Encode -> FFprobe Validation
```

**Independent pause rendering:** a paused source must never pause the whole composition. Reconstruct play and pause intervals per layer, freeze the visual frame during intentional pause, control audio independently per layer policy, rebuild continuous output timestamps, and composite all layers against the master timeline. Segment-based intermediate rendering may be used where it produces more reliable synchronization than one enormous filter graph.

## 21. Export

- **Formats:** MP4/H.264+AAC, WebM/VP9+Opus, MKV, MOV. Future: H.265/HEVC, AV1 — only expose codecs actually available in the local FFmpeg build.
- **Resolutions:** landscape 480p/720p/1080p/1440p/2160p/original-custom; vertical 720×1280, 1080×1920, 1440×2560, 2160×3840; square 1080×1080, 2160×2160. FPS: 24/25/30/50/60. Never expose an impossible combination.
- **Encoder strategy:** prefer a verified hardware encoder, then optimized software, then safer compatibility settings. Never assume NVIDIA/AMD/Intel/Apple hardware exists — detect first.

## 22. Jobs, progress, cancellation

States: `QUEUED → PREPARING → RUNNING → VALIDATING → COMPLETED`; on failure `RUNNING → RECOVERING → RETRY/FALLBACK → FAILED or COMPLETED`; plus `CANCELLED`. Bounded retries only — no infinite loops.

Run FFmpeg with **argument arrays, not shell string concatenation**, and capture machine-readable progress (percentage, elapsed, ETA, current frame, FPS, speed, output size, current stage).

Cancellation must: request graceful FFmpeg termination → wait briefly → force terminate if needed → clean temporary files → preserve originals → mark job `CANCELLED`.

## 23. Recovery, storage safety, security, logging

- **Crash recovery:** store project JSON, timeline JSON, layer definitions, source metadata and export job metadata frequently. On crash: reopen last project, recover safe state, never delete originals, never loop forever.
- **Storage safety:** before export verify free disk space, estimate temp space, verify the output directory and source readability. If space is insufficient, refuse to start and explain required vs available.
- **Security:** sanitize filenames, never build shell commands from raw user strings, use subprocess argument arrays, use random job IDs, restrict backend filesystem operations to configured roots, never expose arbitrary filesystem browsing, validate paths, limit temp file lifetime, validate FFprobe results before rendering.
- **Logging:** structured logs in `storage/logs/`, `projects/`, `proxies/`, `recordings/`, `exports/`, `temp/`. Log startup, FFmpeg detection, FFprobe results, source errors, proxy creation, camera errors, recording events, export stages, recovery attempts and final validation. Keep a concise user-facing diagnostic panel separate from detailed technical logs.

## 24. Self-healing

| Failure | Fallback |
|---|---|
| FFmpeg not found | Search configured/common locations; report exact remediation |
| Camera constraint failure | 1080p → 720p → 480p |
| Preview too heavy | Original → 1080p → 720p → 480p |
| Hardware encoder fails | Software encoder |
| Proxy fails | Retry at lower proxy resolution |
| Export fails | Bounded fallback, preserve all originals |

## 25. Performance principles and UI layout

Priority order: **1. Responsiveness → 2. A/V synchronization → 3. Playback stability → 4. Correctness → 5. Final output quality → 6. Extra UI features.** Never sacrifice synchronization merely to show a higher preview resolution.

Desktop layout:

Mobile: TOP BAR → CANVAS → LAYER LIST → CONTROLS → TIMELINE → STATUS. Usable in Android portrait and landscape.
